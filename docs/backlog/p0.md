# CertBaton P0 Development Backlog

Status: **pre-alpha planning and implementation**

CertBaton is not production-ready. This document defines the first executable
product phase for the free, open-source Windows client. It is an implementation
backlog, not a statement that the listed capabilities already exist.

## Implementation snapshot — 2026-08-04

The source tree has moved beyond the simulation-only walking skeleton. It now
contains strict CLI/IPC target enrollment, protected SSH-key import, exact SSH
host-key pinning, service-owned live operations and scheduling, an embedded
Anvil ACME adapter, external HTTP-01 pre-validation, a fixed Nginx helper
contract, public TLS verification, SQLite write-ahead intents and certificate
metadata, and a live-default WPF status/evidence view.

The complete path is locally tested with fakes, and the helper has an isolated
Linux shim suite. One manually authorized installed-Service workflow has also
passed a real public Let's Encrypt staging order, remote Nginx deployment,
independent public TLS verification, cleanup, durable Service restart check,
and trusted-baseline restoration. WinSCP import, guided enrollment, broad
capability diagnosis, real-target failure injection, outbound alerts,
production-grade retry, a signed MSI, clean-VM qualification, and production
issuance remain open. No item in this snapshot is a production support claim.

## P0 product outcome

P0 is a Windows 11 x64 desktop application and companion Windows Service that
can manage certificate targets, connect to a supported Linux host over
SSH/SFTP, complete an ACME HTTP-01 renewal, deploy the resulting certificate
through a typed web-server recipe, activate it safely, verify the public TLS
endpoint independently, and report failures that require operator action.

The first proven deployment recipe is Nginx. Apache must not be listed as
supported until its complete issuance, deployment, rollback, and verification
workflow passes the same evidence gates.

P0 runs locally. It does not require a CertBaton cloud service and does not
place customer credentials in hosted custody.

## Decisions already made

- Runtime and application stack: .NET 10, WPF desktop application, and .NET
  Windows Service.
- Supported client platform for P0: Windows 11 x64.
- Local UI/service transport: authenticated named pipes; no inbound network
  listener.
- ACME integration: Anvil 3.3.3 behind a CertBaton-owned adapter. It is accepted
  as the pre-alpha candidate; Pebble/public-staging interoperability and
  production protocol behavior remain blocking evidence gates.
- Distribution: machine-wide x64 MSI.
- P0 updates: manually initiated MSI upgrades. An automatic privileged updater
  is not part of P0.
- Telemetry: off by default.
- Deployment automation: typed recipes only. The first pre-alpha recipe uses
  exact-pinned SSH.NET/SFTP and a root-owned Nginx helper with fixed verbs plus
  a canonical transaction UUID. Arbitrary user-provided shell commands are not
  supported.
- Secret storage: DPAPI-NG `LOCAL=user` under the dedicated virtual Service
  account, with protected per-secret files and opaque references. The installed
  lifecycle remains a blocking production qualification gate.
- Persistence: direct `Microsoft.Data.Sqlite.Core` with forward-only,
  checksum-validated migrations, durable operations, intents, certificate
  metadata, and no secret values.

## Definition of priority

- **P0:** required before the first public beta unless a release gate explicitly
  allows a narrower, clearly labeled private alpha.
- **Gate:** a decision or evidence requirement that blocks dependent work or a
  release claim.
- **Acceptance criterion:** an observable pass/fail condition, not an aspiration.

## Ordered epics

### E0 — Repository, architecture, and security contracts

**Priority:** P0

**Dependencies:** None

**Deliverables**

- Public repository governance: license, contribution guide, code of conduct,
  support policy, and responsible disclosure policy.
- Project boundaries for Desktop, Service, Application, Domain, Contracts,
  named-pipe IPC, ACME, SSH/SFTP, deployment recipes, verification, persistence,
  and tests.
- Architecture decision records for the ACME engine, persistence, secret vault,
  logging/redaction, remote privilege model, and MSI toolchain.
- Versioned domain records for targets, connections, ACME accounts, orders,
  deployments, run evidence, and notifications.
- A local integration fixture capable of simulating a disposable Linux/Nginx
  target and common failure modes.

**Acceptance criteria**

- A clean clone restores, builds, and tests without machine-specific paths or
  credentials.
- Domain and application projects do not depend on WPF, a concrete SSH library,
  or a concrete ACME library.
- CI rejects committed secrets, failed tests, license-policy violations, and
  high or critical dependency findings.
- The threat model covers local IPC abuse, credential theft, host-key
  replacement, malicious remote output, command injection, rollback failure,
  log leakage, and update compromise.
- The ACME engine and secret-vault gates have named owners, written evaluation
  criteria, and recorded decisions before their dependent production code is
  merged.

### E1 — Windows Desktop, Service, and authenticated IPC

**Priority:** P0

**Dependencies:** E0

**Deliverables**

- WPF desktop shell and .NET Windows Service.
- Versioned request/response protocol over authenticated named pipes.
- Service ownership of schedules, secrets, remote operations, and run history.
- UI ownership of configuration, approval, monitoring, and diagnostics.
- Restricted service identity and explicitly access-controlled data locations.

**Acceptance criteria**

- An authorized local user can query service health and version from the UI.
- An unauthorized local process cannot submit a configuration-changing request.
- Closing the UI does not interrupt work already owned by the Service.
- Restarting the Service recovers persisted work deterministically.
- An incompatible UI/service protocol version returns a clear upgrade-required
  result instead of failing silently.
- Neither component opens an inbound TCP listener.

### E2 — Inventory, persistence, state machine, and evidence

**Priority:** P0

**Dependencies:** E0, E1

**Deliverables**

- Persistent targets, hostnames, connections, ACME accounts, recipes, schedules,
  run history, and evidence.
- Explicit lifecycle states including unconfigured, diagnostic-only, ready, due,
  running, succeeded, degraded, failed, rollback-required, and blocked.
- Per-stage records for preflight, order, challenge, issuance, deployment,
  activation, verification, cleanup, and notification.
- Transactional schema migrations.
- Exportable redacted diagnostic bundle.

**Acceptance criteria**

- Create, edit, disable, and delete operations preserve referential integrity.
- A process crash at every stage resumes safely or stops in an explainable state;
  it never records an unverified success.
- Every run records stage timestamps, non-secret input identifiers, certificate
  fingerprints, deployment evidence, and final endpoint evidence.
- A diagnostic export contains no password, private key, ACME account key,
  authentication token, or unredacted secret.
- Automated tests upgrade a database from every supported prior P0 schema.

### E3 — Connection enrollment, WinSCP import, and secret protection

**Priority:** P0

**Dependencies:** E1, E2

**Gate:** DPAPI-NG `LOCAL=user` is selected for the pre-alpha Service vault.
Dependent development may proceed, but supported use remains blocked until the
installed identity, reboot, repair/upgrade, backup/restore, rotation,
revocation, and deletion lifecycle passes.

**Deliverables**

- Manual SSH/SFTP connection enrollment.
- Explicit WinSCP metadata import for supported non-secret fields such as host,
  port, username, protocol, key reference, and pinned host-key metadata.
- Import preview and field-by-field confirmation.
- Explicit enrollment of credentials into Service-owned protected storage.
- SSH/SFTP operations for authentication tests, bounded file transfer,
  temporary-file cleanup, and timeouts.
- Credential replacement and revocation workflow.

**Acceptance criteria**

- Import never silently copies or decrypts a stored password.
- The preview displays every field before CertBaton persists the connection.
- A new host key requires explicit trust; a changed pinned key is a hard stop
  during unattended execution.
- Passwords and private keys do not appear in UI output, Service logs, process
  arguments, crash reports, or diagnostic exports.
- An operator can test authentication without changing the remote website.
- A write test is confined to an explicitly selected directory and removes its
  temporary artifact.
- Independently enrolled credentials can be revoked independently.
- Missing WinSCP data or an unsupported profile format leaves existing
  CertBaton configuration unchanged.

### E4 — Read-only capability diagnosis and plan generation

**Priority:** P0

**Dependencies:** E3

**Deliverables**

- Read-only discovery of operating system, SSH/SFTP capability, challenge-path
  writability, web-server type, certificate locations, validation operation,
  activation method, and required privilege.
- Public DNS and HTTP reachability checks needed for HTTP-01.
- Capability classification: full lifecycle, validation-only, deployment-only,
  monitoring-only, or unsupported.
- Human-readable plan preview with typed operations and paths.
- Drift detection that invalidates unsafe prior assumptions.

**Acceptance criteria**

- Diagnosis makes no persistent remote change.
- SFTP-only access is never labeled as capable of certificate activation.
- Missing privilege, unwritable challenge path, DNS mismatch, unreachable
  HTTP-01 endpoint, and unknown web server produce distinct remediation.
- The plan identifies every remote path and typed operation before unattended
  execution can be enabled.
- Unknown platforms stop at diagnosis and never fall back to an arbitrary
  command.
- A changed server type, path, privilege, or activation method returns the
  target to a state requiring review.

### E5 — Embedded ACME account, HTTP-01, and issuance

**Priority:** P0

**Dependencies:** E3, E4

**Gate:** Anvil 3.3.3 is selected as the embedded pre-alpha engine after the
initial source, license, dependency, and adapter review. Supported use remains
blocked on Pebble/Let's Encrypt staging interoperability, protocol failure and
retry evidence, and dependency maintenance review. External Certbot invocation
is not the P0 architecture.

**Deliverables**

- CertBaton-owned ACME adapter and engine-neutral test contract.
- ACME staging and production directory selection.
- Account creation/reuse, terms acknowledgement, order creation,
  authorization, HTTP-01 token placement, polling, finalization, chain storage,
  and cleanup.
- Renewal-window calculation with jitter and duplicate-order protection.
- Handling for bad nonce, rate limits, clock skew, network interruption, and
  ACME problem responses.

**Acceptance criteria**

- A staging order completes end to end against the disposable integration
  target.
- Challenge files exist only in the configured webroot and are removed after
  success or failure.
- CertBaton verifies the challenge URL externally before requesting ACME
  validation.
- Concurrent triggers cannot create duplicate active orders for one target.
- Account and certificate private keys are stored only through the selected
  vault abstraction.
- Rate limits and ACME problem responses become actionable, bounded failures;
  the Service does not retry aggressively.
- Switching from staging to production requires an explicit operator action
  until the production release policy is approved.

### E6 — Safe Nginx deployment, activation, and rollback

**Priority:** P0

**Dependencies:** E4, E5

**Deliverables**

- Typed Nginx deployment pipeline:
  1. Preflight.
  2. Back up current certificate state.
  3. Upload to temporary paths.
  4. Apply prescribed ownership and permissions.
  5. Confirm certificate/private-key pairing.
  6. Validate Nginx configuration.
  7. Replace files atomically.
  8. Reload through the approved typed operation.
  9. Verify the public endpoint.
  10. Commit or roll back.
- Narrow remote privilege contract.
- Bounded and integrity-checked backups.
- An Apache recipe may be developed later, but it earns a support claim only by
  passing all equivalent criteria.

**Acceptance criteria**

- A mismatched certificate and private key are rejected before activation.
- A failed configuration validation leaves the prior deployment active.
- A failed reload or failed public verification restores the previous files and
  attempts the known-safe reload operation.
- Certificate private keys never become world-readable.
- Remote paths and operation parameters cannot inject shell syntax.
- Success requires the live endpoint to present the expected hostname,
  certificate fingerprint, chain, and validity period.
- A successful file copy followed by a stale public certificate is recorded as
  failure, not success.
- A rollback drill restores a working endpoint in the automated integration
  fixture.

### E7 — Scheduling, locking, retries, and recovery

**Priority:** P0

**Dependencies:** E2, E5, E6

**Deliverables**

- Service-owned renewal scheduler with jitter.
- Per-target locks, global concurrency limit, bounded exponential backoff, and
  persisted checkpoints.
- Manual check, staging renewal, and authorized production renewal actions.
- Recovery across reboot, sleep, logout, and network changes.
- Safe cancellation boundaries.

**Acceptance criteria**

- Reboot tests at every major stage yield safe continuation or a clearly
  stopped, recoverable state.
- Two simultaneous triggers for one target result in one active run.
- Failure of one target does not prevent unrelated targets from running.
- Loss of access never deletes or replaces a currently working certificate.
- Schedules survive UI closure, logout, reboot, and time-zone or
  daylight-saving changes.
- Cancellation cannot interrupt an atomic replacement window.
- Retry policy has a finite attempt limit and cannot create ACME rate-limit
  pressure.

### E8 — Independent verification, alerts, audit, and operator UX

**Priority:** P0

**Dependencies:** E6, E7

**Deliverables**

- Public TLS probe independent of the remote SSH session.
- Dashboard views for action required, upcoming renewals, healthy targets, and
  partial or unsupported targets.
- Stage-by-stage run timeline and remediation guidance.
- Windows Event Log integration.
- Alert adapter with deduplication, escalation, recovery, and test-alert
  behavior.
- At least one unattended outbound alert channel selected before public beta.

**Acceptance criteria**

- Authentication failure, host-key mismatch, challenge failure, issuance
  failure, activation failure, rollback failure, and endpoint mismatch produce
  distinct alert types.
- Repeated identical failures are deduplicated without suppressing escalation.
- A recovered target emits a resolved event.
- Testing an alert never initiates a renewal.
- The UI cannot show a healthy state based only on local files, transfer
  success, or a successful reload.
- Critical actions are keyboard accessible, and status is not conveyed by color
  alone.
- Telemetry remains disabled unless the operator explicitly opts in.

### E9 — MSI packaging, manual updates, and supply-chain evidence

**Priority:** P0

**Dependencies:** E1 through E8

**Deliverables**

- Machine-wide Windows 11 x64 MSI.
- Clean install, repair, manual upgrade, downgrade protection, and uninstall.
- Release checksums, software bill of materials, dependency/license reports,
  and build provenance.
- Signed release artifacts before public beta.
- GitHub Releases as the authoritative download source.

**Acceptance criteria**

- A clean supported Windows 11 x64 VM installs without developer tools.
- MSI creates the Service, access-controlled data locations, Event Log source,
  and uninstall registration correctly.
- A manually initiated MSI upgrade preserves configuration, protected secrets,
  schedules, and run history.
- A failed upgrade rolls back to the previous working installation.
- Unsigned, tampered, wrong-architecture, and unsupported downgrade packages are
  rejected.
- Uninstall stops and removes the application and Service, and explicitly asks
  whether operational data and credentials should be retained or deleted.
- Installation does not add an inbound firewall rule.
- P0 contains no automatic privileged updater.

### E10 — Tests, documentation, and public-project readiness

**Priority:** P0

**Dependencies:** E0 through E9

**Deliverables**

- Quick start, security model, credential model, supported matrix,

- Unit, protocol, integration, destructive-failure, and clean-VM test suites.

- Redacted support-bundle workflow.

**Acceptance criteria**

## Explicit P0 non-goals

- Hosted SaaS, a central web UI, a cloud control plane, billing, subscriptions,
  or hosted credential custody.
- DNS-01, wildcard certificates, or a broad provider API catalog.
- Plain FTP.
- Browser automation or control-panel scraping.
- Arbitrary user-supplied shell commands or scripts.
- Direct Docker API exposure or root-equivalent container-engine membership.
- Windows/IIS certificate deployment.
- Automatic DNS or firewall changes.
- Default-on telemetry.
- Automatic privileged application updates.
- Automatic modification of an existing production site without an explicit
  typed plan, backup, and operator approval.
- Apache support claims before Apache passes the complete P0 evidence suite.

## Release gates

### Developer preview

- Increment 1 exit criteria pass.
- Core threat model and applicable architecture decisions are reviewed.
- Only simulators and disposable or explicitly authorized test systems are
  permitted; live work begins with Let's Encrypt staging.
- No production certificate issuance is presented as supported.

### Private alpha

- Increment 3 exit criteria pass against ACME staging.
- Host-key mismatch, certificate mismatch, configuration-test failure, reload
  failure, endpoint mismatch, reboot, and network-loss tests pass.
- Scope is labeled Nginx-only unless another recipe has independently passed the
  same suite.
- Pre-alpha limitations are visible in both the UI and documentation.

### Public beta

- Signed MSI, checksums, software bill of materials, provenance, clean-VM
  matrix, manual upgrade rollback, privacy documentation, disclosure policy,
  and redacted support bundle are complete.
- At least one unattended outbound alert channel works.
- Production issuance and renewal have been proven on multiple disposable or
  explicitly authorized Nginx targets.
- No open critical or high security finding remains.
- At least ten independent targets and three non-maintainer testers complete
  successful unattended exercises.
- Apache is omitted from the supported matrix unless its full evidence suite
  passes.
- Telemetry remains opt-in.

### Stable 1.0

- Two genuine unattended renewal cycles complete successfully on independently
  monitored endpoints.
- Restore and rollback drills pass.
- Upgrade from the oldest supported beta preserves data and protected secrets.
- No open data-loss, secret-exposure, or false-success defect remains.
- Signed release artifacts and recovery instructions are independently
  reproducible.
- Measured failure and support rates remain below thresholds recorded before
  the beta begins.

## Remaining blocking decisions and evidence

The following gates are intentionally not hidden by this backlog:

1. Qualify Anvil against Pebble and Let's Encrypt staging, then close its retry,
   `Retry-After`, alternate-chain, revocation, and renewal-information gaps.
2. Qualify DPAPI-NG `LOCAL=user` across installed logoff, reboot, repair,
   upgrade, backup/restore, rotation, revocation, and uninstall.
3. Qualify the exact SSH.NET and fixed-helper contract on real supported Nginx,
   OpenSSH/SFTP, filesystem, sudoers, init-system, and Docker layouts.
4. Select and implement the first deduplicated unattended outbound alert
   channel.
5. Complete persistence retention, corruption, full-disk, backup/restore, and
   process-kill evidence.
6. Select the MSI toolchain and signing process and complete clean-VM lifecycle
   qualification.
7. Define ACME account-key and certificate-key backup, recovery, rotation, and
   deletion behavior.
8. Define and enforce the explicit staging-to-production approval gate.
9. Complete WinSCP non-secret import or defer it explicitly from P0.
10. Decide whether Apache is completed during P0 or deferred without a support
    claim.
