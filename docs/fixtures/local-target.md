# Disposable local SSH/SFTP and Nginx target

Status: **implemented scaffold; container build and runtime smoke test pending a
local Docker engine**

This fixture is a synthetic integration target for CertBaton development. It
does not connect to, inspect, or reuse any live website, saved SSH profile,
certificate, key, Docker volume, or restoration package.

## What it provides

- One source-built Linux container with Nginx, OpenSSH, OpenSSL, and a narrowly
  allowlisted root helper.
- HTTP, TLS, and SSH/SFTP published on loopback only.
- A non-root `fixture` account authenticated only by a development Ed25519 key
  generated at runtime.
- A private synthetic CA, baseline leaf certificate, and distinct candidate
  leaf certificate generated inside the disposable runtime directory.
- A writable HTTP-01 challenge directory and a separate SFTP staging directory.
- Root-owned active and backup certificate directories.
- Nginx and SSH health checks plus a host smoke test that exercises HTTP,
  CA-validated TLS, caller UID, SFTP upload, and public challenge retrieval.
- Host-only failure injection for challenge permissions, configuration
  validation, reload, stale endpoint, and rollback behavior.

The reserved synthetic TLS name is `certbaton-fixture.test`. The certificates
are not publicly trusted and must never be reused outside this fixture.

## Security and isolation

- Compose publishes all three listeners to `127.0.0.1`; there is no wildcard
  host bind.
- The runtime Docker network is internal. The target has no reason to make an
  outbound internet connection.
- The container has a read-only root filesystem and temporary in-memory runtime
  directories.
- Mutable remote files live in a project-scoped Docker named volume so OpenSSH
  strict-mode checks and Unix ownership/modes are real Linux filesystem
  semantics even when the repository is on Windows. The volume is removed by
  the reset command.
- Linux capabilities are dropped and only those required by Nginx, OpenSSH,
  file ownership, process signaling, and the constrained helper are restored.
- No Docker socket, host network, user home, credential store, or unrelated
  host directory is mounted.
- Only the generated client public-key file is mounted into the target. The
  corresponding client private key is never exposed to the container.
- Password, keyboard-interactive, root, forwarding, tunnel, environment, and
  user startup-file SSH features are disabled.
- The only authorized key is generated by `fixture.ps1 init`. Host-mounted
  runtime keys, public PKI output, known-hosts file, and smoke artifacts are
  ignored by Git. Host keys, CA private material, certificates, and remote state
  live in the disposable named volume; only public CA/certificate and host-key
  outputs are copied back to the ignored runtime directory.
- The authorized-keys copy inside the target is root-owned; the non-root remote
  account cannot add another login key.
- The remote account can write the challenge and staging directories. It cannot
  directly replace active certificate files or signal Nginx.
- `doas` permits that account to invoke only
  `/usr/local/sbin/certbaton-fixture-control`. The root-owned helper accepts a
  fixed verb set and fixed synthetic paths.
- Failure injection is not reachable through SSH. It requires local
  container-root access through the Compose project.

This is a test target, not a hardened production SSH appliance. In particular,
the constrained helper uses set-user-ID elevation inside the container, so the
Compose service cannot enable `no-new-privileges`. Loopback binding, synthetic
data, dropped capabilities, an internal network, and absence of sensitive
mounts are the compensating boundaries.

## Immutable base and package caveat

The Dockerfile is built from the official Alpine `3.22.1` OCI index pinned to:

```text
sha256:4bcff63911fcb4448bd4fdacec207030997caf25e9bea4045fa6c8c44de311d1
```

That digest was resolved from the official Docker registry. The build installs
packages from the Alpine repositories, so package resolution can still change
over time. A release-quality fixture should record the produced image digest
and SBOM in CI. Updating the base digest must be an explicit reviewed change,
followed by build, health, smoke, failure, and secret-scan evidence.

## Prerequisites

- Windows PowerShell or PowerShell 7.
- Docker with Linux containers and Compose.
- Windows OpenSSH tools: `ssh-keygen`, `ssh`, and `sftp`.
- `curl`.

No password, private key, certificate, or CA key is stored in the repository.

## Start and verify

From `fixtures/local-target`:

```powershell
.\fixture.ps1 init
.\fixture.ps1 config
.\fixture.ps1 up
.\fixture.ps1 smoke
.\fixture.ps1 connection
```

`init` generates only a fixture-specific client key and runtime directories.
`config` renders and validates the Compose model without contacting a Docker
daemon. `up` builds the pinned-base image, starts the service, waits for Docker
health, and writes a known-hosts entry from the container's exported synthetic
host public key. `smoke` must report a pass before the target is used.

Optional loopback port overrides belong in an untracked `.env` copied from
`.env.example`.

## Synthetic remote contract

The non-root account can use SFTP to these paths:

| Purpose | Synthetic path | Direct access |
| --- | --- | --- |
| HTTP-01 tokens | `/srv/certbaton/webroot/.well-known/acme-challenge` | Read/write |
| Candidate certificate and key | `/srv/certbaton/tls/staging` | Read/write |
| Active certificate and key | `/srv/certbaton/tls/active` | No direct write |
| One rollback snapshot | `/srv/certbaton/tls/backup` | No direct write |

The staging directory initially contains a candidate certificate distinct from
the active baseline certificate. This makes a skipped reload observable.

The exact privileged verbs are:

```text
paths
validate-staged
validate-config
snapshot
activate-staged
restore-snapshot
reload
fingerprint
```

They are invoked over SSH as:

```text
doas /usr/local/sbin/certbaton-fixture-control <verb>
```

The helper rejects symlinks, empty files, oversized certificate/key files,
unparseable material, expired material, and certificate/key mismatch before
activation. It never accepts a caller-supplied path or shell fragment.

A representative safe deployment sequence is:

1. Upload candidate files to the fixed staging directory through SFTP.
2. Run `validate-staged`.
3. Run `validate-config`.
4. Run `snapshot`.
5. Run `activate-staged`.
6. Run `validate-config` again.
7. Run `reload`.
8. Verify the loopback TLS endpoint presents the expected candidate.
9. On any failure, run `restore-snapshot`, `validate-config`, and `reload`, then
   verify the baseline endpoint.

CertBaton must still own orchestration, evidence, stop conditions, and the
decision to roll back. The fixture helper is a narrow test primitive.

## Failure injection

Set one mode at a time:

```powershell
.\fixture.ps1 inject unwritable-challenge
.\fixture.ps1 inject invalid-config
.\fixture.ps1 inject reload-failure
.\fixture.ps1 inject stale-endpoint
.\fixture.ps1 inject rollback-failure
.\fixture.ps1 inject stale-rollback-failure
.\fixture.ps1 inject none
```

| Mode | Injected behavior | Expected CertBaton result |
| --- | --- | --- |
| `unwritable-challenge` | Challenge directory becomes readable but not writable by the SSH account | Preflight/write test fails without changing the active certificate |
| `invalid-config` | A deliberately unknown Nginx directive is included | Configuration validation fails; running endpoint remains unchanged |
| `reload-failure` | Next typed reload returns failure without signaling Nginx | Restore snapshot, reload, verify baseline, and record activation failure |
| `stale-endpoint` | Next typed reload reports success but deliberately skips the signal | Independent TLS verification observes the baseline certificate and rejects false success |
| `rollback-failure` | First reload runs normally; second reload returns failure | A forced post-activation rollback cannot claim success without endpoint evidence |
| `stale-rollback-failure` | First reload is skipped; second reload fails | Stale-endpoint detection is followed by a critical rollback-required result |
| `none` | Removes injection state and restores challenge permissions | Normal fixture behavior |

Reload actions are consumed in order. Reapplying a mode resets all prior
injection state first.

## Reset and removal

```powershell
.\fixture.ps1 down
.\fixture.ps1 reset
```

`down` stops only this named Compose project and preserves its named state
volume. `reset` stops the project and removes that named volume, then resolves,
checks for filesystem reparse points, and validates each deletion target
beneath the fixture directory before removing the known host-runtime
subdirectories. It generates a new client key immediately; the next `up`
creates new SSH host and synthetic TLS identities.

Do not manually point the Compose mounts at another directory. Do not add a
remote Docker context, wildcard host binding, real key, real certificate, live
webroot, or Docker socket to this fixture.

## Validation status

The Compose CLI is available in the initial development environment, but its
Linux-container daemon was not running. The repository scaffold can therefore
be checked with `docker compose config`, static parsing, and secret scanning,
but its image build, health check, SSH/SFTP exchange, TLS handshake, reset, and
failure sequences remain unexecuted until a local engine is started.

The fixture must fail closed if:

- the runtime public key is missing or not exactly one Ed25519 key;
- a required synthetic state file is missing after initialization;
- SSH or Nginx configuration validation fails;
- a generated host identity cannot be exported;
- the Compose project is unhealthy; or
- reset cannot prove its targets are beneath the fixture root.
